# Critical Test Coverage Design

## Goal

Increase confidence in the project by testing the critical user and backend flows first, rather than chasing a coverage percentage. The suite must stay CI-friendly: no external network calls, no real API keys, no required ffmpeg or yt-dlp binaries, and no required macOS Keychain access in newly added tests.

## Current Baseline

- Frontend unit/integration tests: 2 Vitest files, 5 tests.
- Frontend coverage: generated by `npm run test:coverage`; current line coverage is about 21.9%.
- Rust tests: 74 library tests, with 73 passing and 1 ignored when run outside the sandbox with the rustup toolchain path.
- Rust integration tests: one ignored ffmpeg sidecar test.
- Browser tests: one Playwright test under `e2e-pw`.
- CI currently runs `cargo test`, TypeScript check, Vitest, and Vite build. It does not yet run coverage or Playwright.

## Strategy

Use a three-layer test pyramid.

1. Rust unit and integration-style tests with mock HTTP, temp directories, and fixture data. These cover backend parsing, aggregation, file output, provider factories, and command-adjacent logic without external services.
2. Vitest frontend integration tests with mocked IPC and real React components. These cover page workflows, Zustand state transitions, and user interactions.
3. Playwright browser smoke tests with mocked Tauri APIs. These cover a small number of real-browser journeys served by Vite and running in CI.

This keeps fast tests close to the code while still exercising the browser for the workflows most likely to break from routing, rendering, or app boot regressions.

## Frontend Vitest Scope

Add or extend tests for the following critical areas.

- `ProjectsPage`: empty state, project list rendering, opening a project, deleting with confirmation, project status display, and toolchain or first-run messaging where practical.
- `ImportPage`: text project creation, basic validation, navigation to review, and IPC error handling.
- `ReviewPage`: B-Roll point list rendering, start-picking navigation, empty project states, and status labels.
- `PickerPage`: extend existing tests for skip, keyword edit and re-search, progress event handling, download completion, no results, and filters.
- `SettingsPage`: settings load, provider save/test states, validation errors, successful and failed test pings, and model preset behavior.
- `SummaryPage`: completed clip summary, open folder, export EDL/FCPXML actions, and export error handling.
- Pure components and utilities: `VideoGrid`, `KeywordHeader`, `FilterDialog`, `PointStatusBar`, `PreviewPane`, `ProjectFolderCard`, and `src/lib/utils.ts`.

## Frontend Test Infrastructure

Create reusable helpers under `src/test-utils/` so each test file does not hand-roll state and IPC setup.

- Factory helpers: `makeProject`, `makePoint`, `makeVideoCandidate`, and `makeSettings`.
- Rendering helper: `renderWithRouter`, with optional route and initial state.
- Store reset helper for Zustand before each test.
- IPC and Tauri mocks declared at module top level to avoid Vitest hoisting warnings from nested `vi.mock(...)` calls.
- Event helpers for download progress and completion listeners.

The tests should prefer user-visible assertions and realistic events over implementation details.

## Rust Scope

Add high-value tests only where the code is isolable without services.

- `commands`: test project-state transformations through smaller extracted helpers where needed, rather than trying to construct full Tauri runtime state in every case.
- `download_manager`: extend progress parsing and cancellation edge cases.
- `settings_store`: add tests for settings JSON defaults, provider model presets, and model lists. Do not add new Keychain-dependent tests.
- `search`: cover YouTube API duration parsing, stock provider response parsing, error propagation, and multi-source aggregation with fixtures or mock HTTP.
- `transcription` and `ai`: cover provider factories and response parsing with mock HTTP responses.
- `export`: add only regression tests for uncovered output details if gaps are found during implementation.

Existing ignored tests for real ffmpeg or yt-dlp behavior remain ignored and are not required by CI.

## Playwright Scope

Keep Playwright small and high signal.

- App boot with Tauri mocks and an empty projects state.
- Picker journey with mixed search result sources, selected video, and download progress state.
- One settings or import/review journey if it can be mocked cleanly without duplicating too much Vitest coverage.

Playwright tests must use local fixtures and `page.addInitScript` Tauri stubs. They must not call external APIs.

## Playwright Infrastructure

- Add `webServer` to `playwright.config.ts` so `npm run test:pw` starts Vite on port 1420 automatically.
- Keep Chromium as the CI browser target.
- Extract a reusable Playwright Tauri mock helper if multiple specs need the same boot stub.
- Avoid screenshots as required assertions unless testing a visual regression manually; screenshots may remain useful artifacts.

## CI Changes

- Change the frontend unit-test step from `npx vitest run` to `npm run test:coverage`.
- Add Playwright browser installation for Chromium.
- Add `npm run test:pw` after frontend dependencies are installed and before or after `npm run build`.
- Keep `cargo test --manifest-path src-tauri/Cargo.toml`, TypeScript check, and `npm run build`.
- Do not require coverage thresholds in this first pass. Revisit thresholds after the critical-flow tests establish a realistic baseline.

## Verification Commands

The implementation is complete only when these pass in the current workspace:

```bash
npm run test:coverage
npm run test:pw
PATH="$HOME/.cargo/bin:$PATH" cargo test --manifest-path src-tauri/Cargo.toml
npm run build
```

If local sandboxing blocks mock HTTP servers or Keychain access, rerun the Rust command outside the sandbox with the same `PATH`.

## Success Criteria

- Critical user flows have Vitest coverage with stable mocked IPC.
- Critical backend parsing and state behavior have Rust tests with mock or fixture data.
- Playwright runs in CI against a Vite-served app with mocked Tauri APIs.
- No newly added test requires external network access, real provider credentials, installed ffmpeg, installed yt-dlp, or interactive Keychain access.
- Frontend coverage increases as a side effect of useful tests, but no arbitrary threshold is enforced in this phase.
